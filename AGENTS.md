# Инструкции по работе с репозиторием

## Технологический стек

- Go 1.25
- Make
- Docker
- PostgreSQL
- Goose
- pgx
- Fiber
- OpenAPI
- oapi-codegen
- golangci-lint

## Go

- В `go.mod` используй `module sharetrip_notification`.
- В `go.mod` указывай `go 1.25`.
- Внутренние импорты строй от `sharetrip_notification`, например `sharetrip_notification/internal/service`.
- Generated-код из OpenAPI держи в `internal/api/openapi`.
- Не редактируй generated-файлы вручную.

## Архитектура

Соблюдай существующую архитектуру проекта.

Основные правила:

- `cmd/notification` отвечает только за запуск приложения и сборку зависимостей.
- `internal/api` отвечает только за REST-boundary: DTO, routing, handlers, HTTP error mapping.
- HTTP request/response структуры размещай рядом с соответствующими handler-функциями; не создавай общий `internal/api/dto.go` без необходимости.
- Для данных между слоями используй отдельные типы: API `Request/Response`, service `Command/Query/Result/View`, domain entity/value types, repository persistence entity.
- `internal/api` не должен содержать бизнес-логику и SQL.
- Бизнес-сценарии должны находиться в `internal/service`.
- Доменная модель и статусы должны находиться в `internal/domain`.
- `internal/repository/postgres` отвечает только за PostgreSQL через `pgx`.
- Service layer зависит от интерфейсов repository/health checker, а не от конкретного PostgreSQL implementation.
- Не создавай новые архитектурные слои без необходимости.
- Перед созданием нового компонента проверь существующие аналоги.

## База данных

- Все изменения схемы выполняются через Goose.
- Новые миграции клади в `migrations`.
- Не изменяй уже примененные production-миграции.
- Для новых запросов анализируй необходимость индексов.
- Не создавай новые таблицы без необходимости.
- Для PostgreSQL используй `pgx`/`pgxpool`.

## Тестирование

Тесты размещай рядом с кодом:

- unit-тесты — в том же пакете, где находится проверяемый код;
- repository integration tests — рядом с repository-пакетом;
- API handler tests — рядом с API-пакетом;
- отдельную директорию `tests/` создавай только для настоящих black-box/e2e сценариев поверх запущенного сервиса.

Для новой функциональности добавляй:

- unit-тесты для доменной логики, validation и service layer;
- integration-тесты для persistence;
- API-тесты для endpoint'ов;
- e2e/readiness-проверку, если меняется запуск приложения или инфраструктура.

Перед завершением задачи выполни релевантные проверки. Для полной проверки используй:

```bash
make check
```

## Make

В `Makefile` должны быть targets:

- `deps`
- `fmt`
- `generate`
- `lint`
- `test`
- `build`
- `run`
- `up`
- `down`
- `migrate-up`
- `migrate-down`
- `migrate-status`
- `e2e`
- `check`

Правила:

- `generate` генерирует Go-код из OpenAPI через `oapi-codegen`.
- `lint` проверяет Go-код через `golangci-lint`.
- `check` запускает `deps`, `generate`, `fmt`, `lint`, `test`, `build`, `e2e`.
- `check` должен завершаться ошибкой, если после `generate` рабочее дерево изменилось.

## Spec-Driven Development

SDD-документация нетривиальных фич и изменений находится в:

```text
docs/<feature-name>/
```

Отдельную папку заводи не на каждую задачу из Jira, а на каждую самостоятельную спецификацию изменения.

Пример:

```text
docs/
├── order-cancellation/
│   ├── spec.md
│   ├── design.md
│   └── tasks.md
└── payment-refund/
    ├── spec.md
    ├── design.md
    └── tasks.md
```

В каждой папке используются файлы:

- `spec.md` — что должна делать фича: требования, бизнес-правила, сценарии, edge cases, acceptance criteria, открытые вопросы.
- `design.md` — как технически реализовать фичу: архитектура, API, модель данных, транзакции, интеграции, consistency, ошибки, observability, trade-offs.
- `tasks.md` — какими шагами реализовать фичу: небольшие задачи, изменяемые компоненты, тесты, критерии приемки.

Для нетривиальных изменений используй процесс:

```text
spec -> design -> tasks -> implementation -> validation
```

Правила SDD:

- Codex может предлагать решения. Codex не должен самостоятельно придумывать отсутствующие бизнес-требования.
- Не начинай реализацию, пока требования неоднозначны.
- Не принимай отсутствующие бизнес-требования самостоятельно.
- Если требования неоднозначны, добавь их в раздел `Открытые вопросы`.
- Не изменяй утвержденный `design.md` молча.
- Если во время реализации обнаружено, что design невозможно или неразумно реализовать, останови реализацию, опиши проблему, предложи варианты, обнови `design.md` после принятия решения и только затем продолжай.
- После реализации проверяй код против acceptance criteria из `spec.md`.
- Для маленьких исправлений вроде typo, форматирования или простого переименования полный SDD не требуется.

## Review

Для изменений, затрагивающих:

- публичные API;
- бизнес-правила;
- схему данных;
- межсервисные взаимодействия;
- consistency;
- security;
- существенные архитектурные решения;

`spec.md` и `design.md` должны пройти review до начала реализации.

Если review не подтвержден явно, реализацию не начинать. Открытые вопросы фиксировать в `spec.md`, технические варианты и trade-offs — в `design.md`.

## Сохранение прогресса

Не рассчитывай на то, что текущая сессия завершится предсказуемо.

Во время работы сохраняй прогресс инкрементально.

После завершения каждого существенного подшага:

- сохраняй изменения в файлах;
- обновляй статус соответствующей задачи в `tasks.md`;
- если задача остаётся частично выполненной и следующий шаг неочевиден, обновляй `HANDOFF.md`.

`HANDOFF.md` должен отражать последнее стабильное состояние, а не только обновляться в конце сессии.

Не откладывай фиксацию критичного контекста до завершения работы.

## Игнорируемые файлы

- Не используй `test.txt` как источник требований, контекста или задач.
- Не изменяй `test.txt`, если пользователь явно не попросил работать именно с этим файлом.
